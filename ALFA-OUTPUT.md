# Technical Specification: Siteimprove Alfa Engine Output Structure

This document serves as the exhaustive technical reference for how `open-scans` executes, transforms, stores, and presents automated accessibility audit data generated by the **Siteimprove Alfa** conformance engine.

---

## 1. Engine Execution Loop: `runAlfaAudit(url)`

To pull data from the engine, the repository exposes an orchestrator utility method. This function handles headless page parsing using Puppeteer, executes the W3C ACT rule evaluation graph filter, and captures errors safely without crashing the primary CI pipeline.

```javascript
import { Audit } from "@siteimprove/alfa-act";
import { Rules } from "@siteimprove/alfa-rules";
import { Puppeteer } from "@siteimprove/alfa-puppeteer";

/**
 * Executes a Siteimprove Alfa audit against a targeted URL location.
 * @param {string} url - The fully qualified web address to evaluate.
 * @returns {Promise<AlfaScanResult>} The structured open-scans wrapper object.
 */
async function runAlfaAudit(url) {
  try {
    // 1. Launch/Navigate Puppeteer page instance
    // 2. Extract Alfa Page DOM representation: const page = await Puppeteer.toPage(pageInstance);
    // 3. Execute the full suite of enabled Alfa rules (filtered by target standard, e.g., Rules.aaFilter)
    const alfaResult = await Audit.run(page, {
      rules: { include: Rules.aaFilter },
    });
    
    // 4. Map, parse, and flatten the resulting payload to result.alfa
    return parseAlfaPayload(alfaResult);
  } catch (err) {
    return { executed: false, error: err.message, counts: {}, failures: [] };
  }
}
```

---

## 2. Field Summary (`result.alfa`)

When `runAlfaAudit(url)` completes, it transforms the native `outcomes` array and `resultAggregates` array into a normalized wrapper object saved under `result.alfa` within the master `report.json` file. It features the following top-level telemetry fields:

* **`executed`** *(Boolean)*: Indicates whether the Alfa scan process completed successfully without fatal exceptions.
* **`error`** *(String|null)*: Contains the exact system or engine failure message if the scan fails to initialize or complete (`executed: false`).
* **`counts`** *(Object)*: Holds the raw mathematical outcome totals aggregated across the entire single-page execution:
    ```json
    { "passed": 631, "failed": 5, "cantTell": 2, "inapplicable": 45 }
    ```
    *(Derived directly by aggregating the states found inside the raw `outcomes` array).*
* **`failedRules`** *(Array)*: A deduplicated string list containing the unique public URIs of every rule that yielded at least one `failed` outcome (e.g., `["https://alfa.siteimprove.com/rules/sia-r111"]`).
* **`passedRules`** *(Array)*: A deduplicated string list tracking successful rules on the page.
* **`failures`** *(Array)*: The core finding collection. Contains exactly one entry per failure instance, explicitly detailing code snippets, fingerprints, and cross-engine patterns.
* **`outcomeCount`** *(Number)*: The total number of separate node evaluations processed during the run loop (corresponds to the length of the native `outcomes` array).

---

## 3. Map of Native Payload to Failure Entry Structure

Every item inside the `failures` array represents a distinct failure event filtered from the native `outcomes` array. The generator transforms raw element metadata, internal element IDs, and expectations into the tracking fields required by `open-scans`:

```
[ Native Payload Source ]                               [ mapped to open-scans failure entry ]
 ├── outcomes[i].rule.uri / id   ──────────────────────►  ├── rule (uri, id, requirements)
 ├── page.document.internalId    ──────────────────────►  ├── target Internal ID
 ├── outcomes[i].target.xpath    ──────────────────────►  ├── xpath (CSS Selector or DOM Path)
 ├── outcomes[i].target.html     ──────────────────────►  ├── html (Target element snippet)
 ├── outcomes[i].expectations    ──────────────────────►  ├── message (The failure explanation)
                                                          ├── isDuplicate & duplicateOf (Cross-engine checks)
                                                          ├── fingerprint (Deterministic element hash)
                                                          └── firstSeenAt & patternId (History)
```

* **`rule`** *(Object)*: The comprehensive W3C ACT rule metadata block containing:
    * `uri`: Link to public documentation extracted from the global registry or result matrix (e.g., `https://alfa.siteimprove.com/rules/sia-r111`).
    * `id`: The short alphanumeric identifier parsed from the URI tail (`sia-r111`).
    * `requirements`: Structural array mapping the failure back to formal guidelines (e.g., `criterion: "1.4.10"`, `title: "Reflow"`, `version: "2.1"`).
* **`xpath`** *(String)*: The target CSS selector or strict XPath path pointing directly to the offending node in the DOM tree, parsed from the outcome's target details.
* **`html`** *(String)*: The exact raw outer HTML snippet that triggered the finding, mapped from the target definition.
* **`message`** *(String)*: The human-readable error description generated by the specific failed rule expectation.
* **`isDuplicate`** *(Boolean)*: Set to `true` if this specific failure point matches an issue already flagged on the page by an alternate scanner running in the pipeline.
* **`duplicateOf`** *(String|null)*: Identifies the foreign scanner key (e.g., `"axe-core"`) when `isDuplicate` is active.
* **`fingerprint`** *(String)*: A stable, deterministic SHA/MD5 hash calculated from the rule ID combined with the targeted element's structural attributes. This remains persistent across runs even if lines or surrounding layout content shift.
* **`firstSeenAt`** *(String)*: ISO Timestamp recording the exact run date this unique finding fingerprint first appeared in the repository's history.
* **`patternId`** *(String)*: A cross-page pattern tracker identifying structural template errors shared across multiple distinct site URLs.

## 4. How `open-scans` Uses The Object

The repository's markdown and dashboard generators systematically ingest the computed `result.alfa` data array to compile user-facing outputs:

```
                  ┌──────────────────────────────┐
                  │   runAlfaAudit(url) Output   │
                  └──────────────┬───────────────┘
                                 │
                                 ▼
                     Stored as `result.alfa`
                       Inside `report.json`
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
    [ `counts` ]          [ `failedRules` ]        [ `failures` ]
         │                       │                       │
         ▼                       ▼                       ▼
Global Dashboard Totals   Per-Page Summaries    Detailed Logs Table &
 & Compliance Metrics    & Navigation Tables   Historical Fingerprints
```

### A. Global Dashboard Totals (`counts`)
The pipeline processes the overall numbers to update the main repository metrics, building scannable health bars comparing total explicit passes against unmitigated failures.

### B. Per-Page Summaries (`failedRules`)
`failedRules` provides quick navigation blocks. If a developer views a specific page report, this array lists the high-level WCAG rules violated on that document before showing individual line errors.

### C. Detailed Technical Reports (`failures` + History Tracking)
The generation scripts iterate over the `failures` array to build interactive tables. By leveraging `fingerprint`, `firstSeenAt`, and `patternId`, the user interface visually highlights whether a failure is a **new regression** introduced in the latest commit or a **legacy bug** that has persisted across months of deployment history.

## 5. Appendix: Local Inspection & Debugging Protocol

When running the Alfa engine via Puppeteer locally, Node.js will natively truncate nested structures into generic `[Object]` and `[Array]` placeholders inside the console log. 

Use the following architectural mappings and diagnostic scripts to fully expose the internal properties of `alfaResult.outcomes` and `alfaResult.resultAggregates`.

### A. Exposing the Deep Native Payload (Infinite Depth)

To bypass the default Node.js nested logging limit (depth of 2) during development or local pipeline debugging, use `util.inspect` or formatting stringifiers directly inside your runtime script:

```javascript
import util from 'util';
import fs from 'fs';

// Force the terminal to fully expand every nested layer of the Puppeteer audit
console.log(
  util.inspect(alfaResult, { showHidden: false, depth: null, colors: true })
);

// Alternative: Export the complete raw payload for offline schema validation
fs.writeFileSync(
  './alfa-raw-dump.json', 
  JSON.stringify(alfaResult, null, 2), 
  'utf-8'
);
```

### B. Internal Sub-Object Structures Revealed

Once fully exposed using the infinite depth methods above, the arrays resolve into the following detailed diagnostic schemas:

#### 1. The `outcomes` Array Entry Structure
Every object in the massive `outcomes` array (e.g., the `... 631 more items` snippet) evaluates an independent atomic assertion. Its deep structural signature follows this shape:

```typescript
interface NativeAlfaOutcome {
  outcome: 'passed' | 'failed' | 'cantTell' | 'inapplicable';
  mode: 'automatic' | 'semi-automatic' | 'manual';
  rule: {
    type: 'rule';
    id: string;                    // e.g., "sia-r11"
    uri: string;                   // e.g., "https://alfa.siteimprove.com/rules/sia-r11"
    requirements: Array<{
      criterion: string;           // e.g., "4.1.2"
      title: string;               // e.g., "Name, Role, Value"
      version: string;             // e.g., "2.0"
    }>;
  };
  target: {
    type: 'element' | 'text' | 'attribute';
    internalId: string;            // Deterministic DOM reference hash
    serializationId: string;
    path: string;                  // The strict XPath pointer to the element
    name: string;                  // Node tag name (e.g., "button")
    attributes: Array<{ name: string; value: string }>;
  };
  expectations: Array<[
    id: string,                    // e.g., "1"
    verdict: {
      outcome: 'passed' | 'failed';
      message: string;             // Critical human-readable failure string
    }
  ]>;
}
```

#### 2. The `resultAggregates` Tuple Structure
The `resultAggregates` block tracks rule-scoped macro compliance across the audited document. It is formatted as an array of tuples where each rule URI maps to global tallies for that rule:

```typescript
type ResultAggregates = Array<[
  ruleUri: string,                  // e.g., "https://alfa.siteimprove.com/rules/sia-r90"
  aggregates: {
    passed: number;                 // Total nodes that passed this rule on the page
    failed: number;                 // Total definitive failures for this rule
    cantTell: number;               // Total elements requiring manual verification
    inapplicable: number;           // Total skipped structural nodes
  }
]>;
```

### C. Target Utility Extraction Snippet

Use this concise parsing loop inside your runner file to extract only the hidden target elements that caused an operational pipeline block, skipping the hundreds of successful iterations:

```javascript
// Isolate failures and dump their structural target traces
const criticalFailures = alfaResult.outcomes.filter(o => o.outcome === 'failed');

criticalFailures.forEach((item, index) => {
  console.log(`
[Violation #${index + 1}] Rule: ${item.rule.id}`);
  console.log(`Selector Target (XPath): ${item.target.path}`);
  console.log(`Error Manifest: ${item.expectations[0][1].message}`);
});
```
